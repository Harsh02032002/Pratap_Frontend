# System upgrades

- 2026-10-20 — Add a route-by-route role/ownership checklist to the backend repo's QA pass. QA-005 and QA-006 came from routes with `protect` but no `authorize`. A script that lists every route and its guards would catch these before release.

- 2026-10-22 — Add a pre-build secret scan over `public/` to the deploy script. SEC-02 shipped because Vite copies `public/` verbatim into every build, so anything dropped there is publicly downloadable with no code review gate. A `gitleaks detect --no-git public/` (or a grep for `password:`/`token`/`@gmail.com`) wired into `deploy_server.sh` before `build:all` would have blocked this release instead of relying on a human audit months later. Same scan should fail CI, not just warn.

- 2026-10-22 — Add an ESLint rule (or a grep in CI) that bans bare `fetch(` inside `src/pages/**`. API-05 existed because three HTTP layers coexist and raw `fetch` silently skips auth — nothing structurally prevents the next one. Allow `fetch` only in `src/utils/api.js` / `src/services/api.js` / `src/api/**`, and require pages to use `fetchJson` or pass `getAuthHeader()`. Note ESLint currently only lints `.ts`/`.tsx`, so this needs `--ext .jsx` added first, which would also surface the ~20 unused-import hints already sitting in these two files.

- 2026-10-22 — Add `"test": "node --test src/**/*.test.mjs"` to package.json scripts. The repo has real tests (imageCompression.test.mjs, 32 of them) but no script to run them, so nobody does — and two of its API-contract tests have been silently failing since RolesPermissions.jsx was rewritten to drop its profilePhoto upload. A one-line script plus a CI step would have caught that drift the day it happened. Those two assertions need updating or deleting: they assert an upload exists in a file that no longer uploads.

- 2026-10-22 — Review large diffs before they land under a misleading message. Commit 537062e ("Fix Android splash screen missing color") rewrote support_tickets.jsx (365 lines deleted) and silently dropped the whole Review modal while keeping the Review buttons, so they set state nothing reads. A cheap guard: `git diff --stat` in the pre-push step, and flag any commit that deletes >100 lines from one file with a message that does not mention that file or feature. Turning on `no-unused-vars` for .jsx (ESLint currently skips them) would also have flagged `selectedItem` as set-but-never-read.

- 2026-10-22 — Make fetchJson (src/utils/api.js ~line 173) surface the backend's `error` field, not only `message`/`details`. The backend's catch blocks reply `{ message: 'Failed to create property', error: err.message }`, where `error` holds the real cause (e.g. a Mongoose validation message), but fetchJson only appends `details`, so every owner sees a generic failure and nobody can diagnose it without opening the Network tab. One line there would improve every page at once. The owner AddPropertyWizard also swallows the message in its own catch (`alert('Failed to submit…')`), so it needs to show `error.message` too.

- 2026-10-22 — Pick ONE employee identifier and enforce it. Property.assignedTo is an ObjectId, but backend auto-assign (propertyController.js:273) stores the employee's loginId ("RYPALA9917"), so every owner "Add Property" crashes with a CastError, and the Support-page Assign popup was changed from emp._id to emp.loginId in the same restyle commit that deleted the Review modal. Meanwhile notifications/FCM key on loginId and employee scoping (scopeHelpers.js) matches assignedTo as an ObjectId. A tiny shared helper (`employeeRef(emp) -> { id, loginId }`) used by every assignment site would make the mix-up impossible, and a unit test that runs `new Property({ assignedTo: <value> }).validateSync()` on the auto-assign output would have caught this on 22 Sept.

- 2026-10-24 — Let the reviewer type a rejection reason on the Support page (and make room rejections tell the owner). The Reject buttons now work, but handleRejectPropertyEdit sends the hard-coded reason "Rejected by admin", so the owner's notification reads "Reason: Rejected by admin" and gives no guidance on what to fix; rejectRoomChanges (backend) stores no reason and sends no notification at all. A small reason box in the Review modal, passed through to both endpoints, would turn a dead-end rejection into something the owner can act on and resubmit.

- 2026-10-27 — Add a superadmin "dry run" for the agreement expiry job before deploying rule changes. The job now auto-exits tenants (bed freed, login off) the day after an un-extended agreement ends, and the first run after deploy will exit every already-expired tenant at once. A read-only `GET /api/admin/agreement-expiry/preview` that runs `getAgreementCycle` + `getExpiryAction` over all active tenants and returns "will exit / grace / skipped (no agreement on record)" counts per owner would let the team see exactly who gets locked out before the 09:00 IST run, instead of finding out from owner complaints.

- 2026-10-27 — Store a rent "price version" on every agreement and extension. Today a room price hike (Room.price 5000 → 6000) only reaches new joiners via the onboarding prefill, and Agreement Extension #n carries only months/dates, so its PDF and every future invoice keep the tenant's old `agreedRent`. Adding `newRent` to `agreementExtensions[]` (defaulting to the room's current price, editable by the owner, shown to the tenant before they sign) and applying it to `tenant.agreedRent` only from `newStartDate` would make "old rent until the agreement ends, new rent from the extension" a rule the system enforces instead of something the owner has to remember to edit by hand.

- 2026-10-27 — When an owner saves a new room price, show "3 tenants in this room are still on ₹5000 — their new rent starts when they extend (15 Nov, 2 Jan, 10 Mar)". Extensions now pick up the room's current price automatically, but the owner gets no feedback at the moment they change the price, so they may think it applied to everyone right away and chase tenants for the difference. The room PUT response already has the room id; one `Tenant.find({ room, status: 'active' }).select('name agreedRent digitalCheckin.agreementDetails agreementExtensions')` plus `getAgreementCycle` gives the list.
